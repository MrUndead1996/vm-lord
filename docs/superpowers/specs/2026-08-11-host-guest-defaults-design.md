# TASK-60: отображение хостовых locale, раскладки и timezone

Дизайн чтения трёх настроек Windows — локали, раскладки клавиатуры и часового
пояса — и их отображения в то, что понимает Linux-гость: POSIX-локаль, XKB-имя
раскладки и IANA-зону. Подзадача эпика #3 «Provisioning Linux», предпоследняя:
всё, что потребляет эти значения, уже написано.

## Задача

Форма создания VM показывает три поля — locale, keyboard, timezone — и
заполняет их из `GuestDefaults` (`ui/src/lib.rs:207-220`). Сегодня туда
приходит `GuestDefaults::default()`: `en_US.UTF-8`, `us`, `Etc/UTC`. Для
пользователя с русской Windows все три значения неверны, и все три он правит
руками при каждом создании.

В объём входит одно: прочитать настройки Windows и отобразить их в
`GuestDefaults`, который композиционный корень передаёт в уже существующий шов
`WorkspaceApp::with_guest_defaults` (`app/src/lib.rs:133`).

Вне объёма: сами поля формы, их валидация, попадание значений в cloud-config —
это #65, #57 и #58, всё уже сделано. Ниже этого дизайна не меняется ни один
существующий файл, кроме одной строки в `crates/vmlord/src/main.rs`.

## Ключевое решение: чтение хоста — там же, где чтение DNS хоста

Три функции чтения — это Win32 и `unsafe`, то есть `crates/platform`,
единственный крейт с `unsafe_code = "allow"`. Прецедент прямо рядом:
`platform::host_dns` читает резолверы *хоста*, а не VM, и лежит именно здесь.

Новый модуль `crates/platform/src/host_guest_defaults.rs` с единственной
публичной функцией:

```rust
pub fn host_guest_defaults() -> GuestDefaults;
```

Внутри модуль делится надвое, и это деление — главное, что делает задачу
тестируемой:

* **три функции чтения** — каждая трогает ровно один Win32-вызов и возвращает
  сырую строку хоста в `Option`;
* **три функции отображения** — чистые, `&str -> Option<String>`, ничего не
  знают ни про Windows, ни про `unsafe`, и проверяются юнит-тестами на
  фиксированных входах.

Собирает их `host_guest_defaults`: для каждого из трёх полей — прочитать,
отобразить, а на любом промахе взять соответствующее поле
`GuestDefaults::default()`. Поля независимы: нечитаемая раскладка не отменяет
правильно прочитанный часовой пояс.

## Timezone

`GetDynamicTimeZoneInformation` (`Win32_System_Time`) заполняет
`DYNAMIC_TIME_ZONE_INFORMATION`; берётся поле `TimeZoneKeyName` — Windows-ID
вида `Russian Standard Time`.

Берётся именно `TimeZoneKeyName`, а не `StandardName` из соседнего
`TIME_ZONE_INFORMATION`. `StandardName` локализован: на русской Windows там
«Русское стандартное время», которого нет ни в одной CLDR-таблице.
`TimeZoneKeyName` — инвариантный ключ реестра, он одинаков на любой локали.
Крейт `localzone` читает как раз `StandardName` и потому на нелатинской Windows
молча отдаёт `None`; это, вместе с его зависимостью от `windows` 0.54 рядом с
нашей 0.61, снимает его с рассмотрения. `time-tz` решает обратную задачу —
правила перехода по IANA-имени — и Windows-ID не принимает вовсе.

Отображение — крейт **`windows-timezones` 0.5.1**, генерённая из CLDR таблица:

```rust
"Russian Standard Time".parse::<WindowsTimezone>()?.tzdb_id()  // "Europe/Moscow"
```

При `default-features` он тянет ноль зависимостей (фича `std` включает только
`Display`, `FromStr` и `Error`), лицензия — `(MIT OR Apache-2.0) AND
Unicode-DFS-2016`. Ключ `UTC` в таблице есть и даёт `Etc/UTC`, что совпадает с
нашим дефолтом.

Промах — пустой `TimeZoneKeyName`, ненулевой код возврата или ID, которого нет
в таблице (Windows выпускает новые зоны быстрее, чем обновляется крейт).

## Locale

`GetUserDefaultLocaleName` (`Win32_Globalization`) отдаёт BCP-47:
`ru-RU`, `en-US`, `pt-BR`, `zh-Hans-CN`, `sr-Latn-RS`.

Отображение в POSIX — разбор по дефису на субтеги:

1. первый субтег — язык, две-три буквы;
2. следующий, если это ровно четыре буквы, — письменность;
3. следующий, если это ровно две буквы, — регион.

Результат — `{язык}_{РЕГИОН}.UTF-8`, регион в верхнем регистре. Письменность
отбрасывается, кроме двух пар, где она и есть смысл различия: `sr` + `Latn` и
`uz` + `Cyrl`. Для них имя берётся в том виде, в каком оно записано в
glibc-овском `SUPPORTED`, — с модификатором и *без* кодировки: `sr_RS@latin`,
`uz_UZ@cyrillic`. Именно это имя получает `locale-gen`, и совпадать оно должно
с `SUPPORTED`, а не с выводом `locale -a`. Для `zh` письменность отбрасывается
как везде: `zh-Hans-CN` → `zh_CN.UTF-8`, регион уже всё сказал.

Промах — тег без региона (`en`) или с регионом из UN M.49 (`es-419`): POSIX
требует пару «язык + территория», и выдумывать территорию за пользователя
неправильно. Промах — и тег, не разобравшийся по правилам выше.

Проверять получившееся имя по списку локалей, которые собраны в конкретном
образе, здесь нечем и незачем: cloud-init на неизвестной локали ограничивается
записью в свой лог, гость при этом грузится.

## Keyboard

`GetKeyboardLayoutNameW` (`Win32_UI_Input_KeyboardAndMouse`) отдаёт KLID —
восемь шестнадцатеричных цифр, `00000419`. Это раскладка вызывающего потока; в
композиционном корне, до создания окна, она равна раскладке пользователя по
умолчанию.

Крейта KLID → XKB не существует, поэтому таблица своя. Четыре ступени:

1. точное совпадение KLID в таблице частотных раскладок;
2. тот же поиск с обнулённым старшим словом: `00020409` (US-International) и
   `00010419` (Russian Typewriter) — варианты базовых раскладок, и базовая
   даёт верный XKB-ответ там, где вариант нам неизвестен;
3. поиск по первичному языку — младшие десять бит LANGID — в маленькой второй
   таблице: это ловит подъязыки, которых нет в первой (`00000c0a`, испанский
   вариант → `es`);
4. `us` и `log::warn!` с исходным KLID.

Первая таблица — полсотни раскладок: `00000409` us, `00000809` gb,
`00000407` de, `00000807` ch, `0000040c` fr, `0000080c` be, `00000c0c` ca,
`0000040a` es, `0000080a` latam, `00000410` it, `00000816` pt, `00000416` br,
`00000413` nl, `0000041d` se, `00000406` dk, `00000414` no, `0000040b` fi,
`0000040f` is, `00000415` pl, `00000405` cz, `0000041b` sk, `0000040e` hu,
`00000418` ro, `00000402` bg, `0000041a` hr, `00000424` si, `0000081a` rs,
`00000c1a` rs, `00000419` ru, `00000422` ua, `00000423` by, `0000043f` kz,
`00000408` gr, `0000041f` tr, `0000042c` az, `0000040d` il, `00000401` ara,
`00000429` ir, `0000041e` th, `00000411` jp, `00000412` kr, `00000804` cn,
`00000404` tw, `0000042a` vn, `00000425` ee, `00000426` lv, `00000427` lt,
`00000439` in, `0000042f` mk, `0000041c` al.

Раскладка выдаётся одним значением, без второй латинской и без переключателя.
`seed::user_data::keyboard_file` пишет `XKBOPTIONS=""` жёстко
(`seed/src/user_data.rs:92`), так что `us,ru` в консоли гостя не переключалось
бы ничем; пара «вариант + переключатель» — отдельная подзадача эпика, вместе с
пустующим `XKBVARIANT`.

## Композиционный корень

`crates/vmlord/src/main.rs`, при построении приложения:

```rust
let mut application = vmlord_app::WorkspaceApp::new(repository)
    .with_guest_defaults(vmlord_platform::host_guest_defaults())
    .with_image_picker(...)
```

Чтение однократное, при старте. Настройки Windows во время работы приложения
меняются редко, а форма всё равно даёт править любое из трёх полей.

## Логирование

* `DEBUG` — что именно прочитано с хоста и во что отобразилось, по строке на
  поле: `the host locale ru-RU maps to ru_RU.UTF-8`.
* `INFO` — одна итоговая строка со всеми тремя значениями, которые получит
  форма.
* `WARN` — каждый промах, с исходным значением хоста и с тем дефолтом, который
  подставлен взамен.
* `ERROR` — не используется: ни один исход этого модуля не мешает работать.

## Тестирование

Юнит-тесты в модуле, на чистых функциях отображения:

* локаль: `ru-RU` → `ru_RU.UTF-8`; `pt-BR` → `pt_BR.UTF-8`; `zh-Hans-CN` →
  `zh_CN.UTF-8`; `sr-Latn-RS` → `sr_RS@latin`; `en` → `None`; `es-419` →
  `None`; мусор → `None`;
* раскладка: `00000419` → `ru` (ступень 1); `00020409` → `us` (ступень 2);
  `00000c0a` → `es` (ступень 3); `0000ffff` → `us` (ступень 4); не-hex → `us`;
* часовой пояс: `Russian Standard Time` → `Europe/Moscow`; `UTC` → `Etc/UTC`;
  `No Such Standard Time` → `None`; пустая строка → `None`.

Плюс тест на сборку: `GuestDefaults`, собранный из трёх `None`, равен
`GuestDefaults::default()` — это и есть обещание «неизвестное значение не ломает
создание VM». Чтобы его написать, сборочная функция принимает три `Option` и
отделена от той, что дёргает Win32.

Функции чтения юнит-тестами не покрываются: их результат — это настройки машины,
на которой идёт сборка. Проверка — ручная, владельцем проекта, на реальной
Windows: значения в форме создания совпадают с тем, что стоит в системе.

## Критерий выхода

На русской Windows форма создания VM открывается с `ru_RU.UTF-8`, `ru` и
`Europe/Moscow` без единой правки руками, и каждое поле по-прежнему правится.
На хосте, где любая из трёх настроек не читается или не отображается, форма
открывается с дефолтом по этому полю, в логе есть `WARN` с исходным значением, а
остальные два поля верны.
