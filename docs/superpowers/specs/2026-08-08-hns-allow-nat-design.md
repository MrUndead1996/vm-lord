# TASK-44: снятие запрета NetworkMode::Nat

Дизайн снятия запрета на `NetworkMode::Nat` на границе домена. Часть
декомпозиции эпика #5 «Миграция HNS: базовая сетевая интеграция»; опирается на
#43 (общая NAT-сеть), #41 (endpoint виртуальной машины) и #38 (подключение
endpoint'а при старте).

## Задача

`VmStartPipeline` умеет выдать VM endpoint и вписать секцию `NetworkAdapters` в
`config.json`, но эта ветка недостижима: `HcsVmConfigBuilder::build` и
`HcsVmRepository::update_vm` отклоняют любой режим, кроме `NetworkMode::None`,
так что все VM создаются с `network_mode: None`. #44 открывает границу для
`Nat` — одним изменением, ровно как обещал дизайн #38.

`External` и `Internal` остаются закрытыми: их поддержка — задача #10.

## Решения

### Что принимает граница

`HcsVmConfigBuilder::build` (создание) и `HcsVmRepository::update_vm`
(редактирование) принимают `None` и `Nat`; `External`, `Internal` и
`Unknown(_)` отклоняются с сообщением, называющим #10 — например «External and
Internal networking arrive with #10». Отказ на границе домена даёт внятную
причину вместо HRESULT, который HNS вернул бы глубже.

Создание по-прежнему не пишет секцию `NetworkAdapters`: её владелец —
`VmStartPipeline` (#38), потому что до первого старта у VM нет ни endpoint'а,
ни MAC. Документ создания от режима не зависит вовсе: `build` режим только проверяет, а
записывает его в `VmComputeSystemMapping::network_mode` уже
`VmCreationPipeline` — это он делает и сегодня.

### Смена режима у существующей VM

`update_vm` сегодня правит только топологию в `config.json`. Он получает один
шаг: если `request.network_mode` отличается от `mapping.network_mode`, мэппинг
перезаписывается через `store.insert`.

Хранилищем режима остаётся `MetadataStore`, а не `config.json`: `VmStartPipeline`
читает `mapping.network_mode`, а сам документ — производная, которую старт
переписывает под текущий режим.

Проверки `refuse_if_live` здесь нет. Смена режима применяется на следующий старт,
как и правка RAM и числа ядер: HCS уничтожает компьют-систему при остановке и
пересоздаёт её из документа, так что работающая VM живёт со своей текущей
конфигурацией до перезапуска.

### Возврат с Nat на None

У VM, которая уже стартовала с NAT, в `config.json` осталась секция
`NetworkAdapters`. Без её удаления смена режима на `None` ничего бы не изменила:
VM поднялась бы с прежним адаптером.

`hcs_config::remove_network_adapter(document)` удаляет ключ `NetworkAdapters` из
`/VirtualMachine/Devices` и возвращает документ без изменений, если ключа там
нет. Ветка «не Nat» в `VmStartPipeline::attach_network` вызывает её и
перезаписывает файл, только если документ изменился — зеркало ветки Nat.

Endpoint в HNS и записанный `endpoint_id` не трогаются. Endpoint живёт до
удаления VM (#42), поэтому возврат на Nat отдаёт гостю тот же адрес; удаление
здесь означало бы новый адрес при каждом переключении и заходило бы на
территорию #42.

### Отчёт о режиме

`HcsVmRepository::summary()` возвращает `mapping.network_mode` вместо
захардкоженного `None`.

Это не косметика. Форма редактирования в UI заполняется из `VmSummary`, поэтому
с константным `None` правка одного лишь RAM у NAT-овой VM молча прислала бы
`network_mode: None` и отключила бы ей сеть на следующем старте.

`gpu_mode` и `ip_address` остаются как есть: адрес гостя — #37, GPU — вне эпика.

### UI

Комбобокс сети в форме редактирования теряет `External` и `Internal` и
сравнивается с формой создания: `NAT` и `None`. Предлагать пункт, который
гарантированно вернёт ошибку, — худший из способов рассказать про #10.

`edit_vm_request` продолжает отклонять `Unknown(_)`: это режим, прочитанный из
чужого бэкенда, а не выбранный пользователем.

Отказ домена остаётся страховкой границы: UI не единственный её вызывающий, и
проверка не должна жить только в нём.

## Тестирование

Unit-тесты `hcs_config`: `build` принимает `Nat`; `build` отклоняет `External`,
`Internal` и `Unknown(_)` с упоминанием #10; документ создания для `Nat` не
содержит `NetworkAdapters`.

Unit-тесты `remove_network_adapter`: секция удаляется; остальной документ не
меняется; документ без секции возвращается как есть; невалидный JSON
отклоняется.

Unit-тесты `VmStartPipeline`: VM с `NetworkMode::None` и устаревшей секцией
`NetworkAdapters` стартует без неё, и файл переписан.

Unit-тесты `repository`: `update_vm` принимает `Nat` и отклоняет остальные
режимы; смена режима попадает в мэппинг; неизменный режим мэппинг не трогает;
`summary()` показывает режим из мэппинга.

Тест UI на `edit_vm_request` перенацелен с `External` на `Nat`.

Ручная parity-проверка на Hyper-V — за владельцем проекта: создать VM с NAT,
стартовать, убедиться в наличии адаптера у гостя.
