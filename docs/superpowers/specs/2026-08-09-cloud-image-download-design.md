# TASK-50: загрузка cloud-образа с кешем и проверкой SHA256

Дизайн загрузчика cloud-образов: блокирующий HTTPS-клиент, кеш на диске с
проверкой контрольной суммы при каждом попадании, докачка через HTTP Range и
публикация прогресса для UI-потока. Часть декомпозиции эпика #48 «Импорт
cloud-образов»; блокирует #53 (резолвер релизов Ubuntu).

Задача самодостаточна: от спайка #49 и от qcow2-ридера #51 она не зависит и
может быть сделана первой в эпике.

## Задача

Эпик получает загрузочный VHDX из официального cloud-образа дистрибутива.
Первый шаг — добыть сам образ и убедиться, что он не повреждён. Это первый
сетевой клиент в проекте, поэтому выбор крейта и модель потоков фиксируются
здесь, а не по ходу реализации.

Вызывающего у загрузчика пока нет: импортёр (#52) и создание VM из cloud-образа
появятся позже, а каталог с выбором релиза эпик прямо выносит за скобки.
Поэтому в объём входит механизм публикации прогресса и его контракт, но не
виджет в egui — рисование прогресс-бара делается отдельной задачей, когда
появится тот, кто загрузку запускает.

## Что делает AppSandbox

`prefetch_build_deps.c` тянет пакеты по plain HTTP и помечает источник в госте
как `[trusted=yes]`. Заимствовать здесь нечего; это прецедент того, как делать
не надо, и причина, по которой ниже транспорт зафиксирован как HTTPS с
проверкой сертификата по хранилищу Windows.

## Границы модулей

Новый крейт `crates/image` (`vmlord-image`). Зависимости: `ureq`, `sha2`,
`log`, `vmlord-core`.

Отдельный крейт, а не модуль в существующем:

* `vmlord-core` — UI-независимые доменные типы, его зависимости ограничены
  `log`, `serde`, `toml`; HTTP-клиент туда не тянем.
* `vmlord-platform` — Windows-специфичный код с `unsafe_code = "allow"`;
  загрузка не требует ни того, ни другого и собирается под любую платформу.

В этот же крейт позже лягут qcow2-ридер (#51) и резолвер релизов (#53).

Побочный полезный эффект: крейт кроссплатформенный, поэтому его тесты, включая
сетевые и тесты на гонку, запускаются нативно в WSL, а не только на Windows.

Тип прогресса и публикатор живут **не** в нём, а в `vmlord-core::progress`: UI
будет их рисовать и не должен ради этого зависеть от HTTP-клиента. Тот же
приём, что с `Diagnostic` — общий словарь в core, реализация снаружи.

## Контракт прогресса

```rust
// vmlord-core::progress
pub struct DownloadProgress {
    pub phase: DownloadPhase,
}

pub enum DownloadPhase {
    Connecting,
    Downloading { downloaded: u64, total: Option<u64> },
    Verifying { hashed: u64, total: u64 },
    Completed,
}

#[derive(Clone, Default)]
pub struct ProgressPublisher(Arc<Mutex<Option<DownloadProgress>>>);

impl ProgressPublisher {
    pub fn publish(&self, progress: DownloadProgress);
    pub fn snapshot(&self) -> Option<DownloadProgress>;
}
```

`publish` затирает предыдущий снимок. Очереди нет намеренно: прогресс — это
уровень, а не поток событий, и потерянное промежуточное значение ничего не
значит. Этим он отличается от `VmEventSink` (`crates/platform/src/watch.rs:85`),
где каждое событие HCS уникально и его потеря — потеря факта.

Отравленный мьютекс восстанавливается через `unwrap_or_else(PoisonError::into_inner)`,
как `VmEventSink::lock` (`watch.rs:143`): снимок — простые владеемые данные,
которые чужая паника не оставит недописанными.

`total: Option<u64>` — сервер вправе не прислать `Content-Length`, и притворяться,
что полный размер известен, нельзя.

Варианта `Failed` в фазах нет. Ошибка — это `Err` из функции загрузки. Держать
её ещё и состоянием снимка значит завести два источника правды, которые могут
разойтись. Джоб-слой, который появится позже, положит `Result` рядом со снимком.
Добавить фазу ожидания или отказа потом можно, не ломая контракт.

### Троттлинг

```rust
pub struct ProgressThrottle {
    publisher: ProgressPublisher,
    min_interval: Duration,   // по умолчанию 100 мс
    last: Option<Instant>,
}
```

Без него каждые 8 КиБ прочитанного потока берут мьютекс — десятки тысяч
блокировок на образ в сотни мегабайт.

Смена фазы и последнее значение внутри фазы публикуются всегда, минуя интервал:
иначе прогресс-бар застывает на 97 % и никогда не показывает переход к проверке
суммы.

`min_interval` — поле, а не константа, поэтому тест выставляет `Duration::ZERO`
и проверяет пропуск без `sleep`.

## Кеш

Content-addressed: имя файла в `image_cache_path` — ожидаемый SHA256 в нижнем
регистре плюс расширение из пути URL (`<hex>.img`), рядом `<hex>.img.part`.

Почему по содержимому, а не по имени из URL: разные релизы Ubuntu носят
одинаковые имена файлов, а суточные сборки — тем более, так что коллизия по
имени неизбежна. При адресации по сумме коллизий нет по построению, и
расхождение «имя против содержимого» невозможно в принципе.

Порядок работы с кешем:

1. Финальный файл есть — считаем его SHA256. Совпал: возвращаем путь, в сеть не
   ходим и лок не берём. Не совпал: WARN, файл удаляется, идём дальше.
2. Открываем `.part`, берём эксклюзивный лок (см. «Гонки»), читаем его длину
   **под локом**.
3. Длина больше нуля — докачка с этого смещения. Ноль или файла не было —
   загрузка с начала.

Отдельной «чистой функции решения» здесь нет намеренно: после того как порядок
зафиксирован локом, решение — это два `if` над длиной файла, и выносить их в
функцию ради тестируемости значит тестировать `if`. Проверяется этот путь
целиком, интеграционными тестами на попадание в кеш, битый кеш и докачку.
Чистыми функциями остаётся то, где действительно есть что разбирать: ответ
сервера и имя файла.

Проверка суммы при каждом попадании в кеш — единственная защита от файла,
усечённого обрывом предыдущей загрузки. Секунды хеширования против повторной
загрузки сотен мегабайт.

## Докачка

При `Resume { from }` уходит `Range: bytes=<from>-`. Разбор ответа — тоже
чистая функция:

```rust
fn resume_decision(
    status: u16,
    content_range: Option<&str>,
    requested_from: u64,
) -> Result<ResumeOutcome, DownloadError>;
```

| Ответ | Решение |
| --- | --- |
| 206 + `Content-Range: bytes <from>-…/<total>`, `<from>` равен запрошенному | дописываем в `.part`, полный размер берём из хвоста заголовка |
| 206 с другим началом диапазона | ошибка: сервер отдал не то, что просили |
| 200 | сервер `Range` проигнорировал; WARN, `.part` усекается в ноль, качаем с начала |
| 416 | `.part` не меньше файла целиком; усекаем его и делаем один запрос без `Range` |
| прочее | `DownloadError::UnexpectedStatus` |

Ветка 416 — это разбор корректного ответа сервера, а не автоповтор при сетевой
ошибке, которого задача не предусматривает. Сетевой сбой даёт ошибку с внятной
диагностикой, повтор инициирует пользователь.

## Завершение загрузки

1. По окончании чтения считается SHA256 самого `.part`.
2. Совпал — `.part` переименовывается в финальное имя. Не совпал — `.part`
   усекается в ноль, возвращается `ChecksumMismatch`, повтора нет.

Порядок именно такой, а не «переименовать, потом проверить»: иначе в кеше
секунду лежит файл с правильным именем и неправильным содержимым, и параллельный
процесс его подхватит.

## Гонки

Имя `.part` детерминированное, значит два загрузчика одного релиза целятся в
один файл. Масштаб ущерба ограничен: перемешанные два потока байт не пройдут
SHA256, так что до импортёра битый образ не доедет ни при каких условиях. На
кону впустую скачанные сотни мегабайт и невнятная диагностика «сумма не
сошлась» там, где на самом деле была гонка.

**Эксклюзивный лок на `.part`** через `std::fs::File::try_lock` (стабилен с
Rust 1.89; тулчейн проекта — 1.97.1, наличие проверено экспериментом).
Зависимость не нужна. Внутри — `LockFileEx` с
`LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY` на Windows и `flock` на
Unix. Два проверенных свойства:

* лок работает и внутри одного процесса — второй `File::open` того же пути
  получает `WouldBlock`, — поэтому один механизм закрывает и два потока, и два
  экземпляра VMLord;
* лок снимается операционной системой при закрытии дескриптора, то есть и при
  аварийном завершении процесса. Файл-маркер `<name>.lock` этого не даёт: он
  переживает падение, и приходится сочинять эвристику протухания по PID или
  таймауту.

Длина `.part` читается уже под локом: иначе между чтением длины и захватом лока
чужой загрузчик успевает дописать файл, и мы запрашиваем не тот диапазон.

Имя `.part` при этом остаётся детерминированным. Уникальное имя на попытку
сняло бы гонку без всякого лока, но лишило бы смысла докачку: следующий запуск
не нашёл бы свой прошлый огрызок.

**Проигравший получает `DownloadError::AlreadyInProgress`** и не ждёт. Ждать
чужую загрузку — политика, и место ей у того, кто запускает джобы и знает,
стоит ли вставать в очередь; внутри функции «скачай файл» она превращается в
таймаут, взятый с потолка. Сейчас у загрузчика нет ни одного вызывающего, так
что сценарий ожидания выдумывать рано.

**`.part` не удаляется, пока лок держится, а усекается в ноль.** Касается ветки
416 и ветки несовпадения суммы. Удаление открытого файла под Windows — отдельный
источник боли, а усечение сохраняет и дескриптор, и лок.

**Перед переименованием проверяется наличие финального файла.** `fs::rename` в
std на Windows идёт через `MoveFileEx` с `MOVEFILE_REPLACE_EXISTING`, то есть
существующий файл молча затирается, а не отвергается. Если финальный файл уже
появился, значит другой загрузчик победил: усекаем свой `.part` и возвращаем
чужой путь. Содержимое у них по построению одинаковое — имя и есть сумма.
Смысл проверки в том, чтобы не пытаться заменить файл, который в этот момент
может быть открыт импортёром на чтение.

**Принятый компромисс.** Остаётся окно: мы проверили сумму кешированного файла и
вернули путь, а другой процесс в этот же момент файл удалил. Удаляет он его
только при несовпадении суммы, то есть в ситуации, когда и наша проверка бы не
прошла; практически это означает `NotFound` у вызывающего вместо чистой ошибки.
Удерживать лок на финальном файле через весь импорт ради этого не стоит.

## Отмена

Флаг `Arc<AtomicBool>`, по образцу `running` в `crates/platform/src/dhcp.rs:239`,
проверяется между чанками чтения и между чанками хеширования. Даёт
`DownloadError::Cancelled` и **оставляет `.part` на месте**, чтобы следующий
запуск докачал, а не начал заново.

Без отмены загрузка на сотни мегабайт неостановима, а стоит она десяток строк.

## Транспорт

`ureq` 3.4.0. Блокирующий, без async-рантайма; `body_mut().as_reader()` даёт
`Read`, который скармливается циклу чтения с подсчётом байт.

`reqwest::blocking` отвергнут: под ним всё равно tokio, а в проекте нет ни
tokio, ни единого `.await`, и единственный фоновый поток — DHCP-воркер.

Ручной клиент поверх `WinHttp` отвергнут: он дал бы системный прокси и хранилище
сертификатов даром, но ценой сотен строк FFI и `unsafe` в крейте, которому
Windows API иначе вообще не нужен.

Фичи:

* `platform-verifier` — доверие к сертификатам берётся из хранилища Windows, а
  не из вкомпилированного набора корней; иначе корпоративный MITM-прокси ломает
  загрузку намертво.
* `win-system-proxy` — прокси берётся из системных настроек Windows.

Явные таймауты на соединение и на чтение: зависший сервер иначе вешает рабочий
поток навсегда.

SHA256 — `sha2` 0.11.

## Модель доверия

Целостность даёт SHA256, аутентичность — HTTPS. Список контрольных сумм,
скачанный с того же сервера, аутентичности не даёт: тот, кто подменил образ,
подменит и список. Проверка GPG-подписей — усиление за пределами эпика.

## Ошибки

Свой `DownloadError` с `Display` и `std::error::Error`, по образцу
`SettingsError` (`crates/core/src/settings.rs:150`). Никаких `anyhow` и
`Box<dyn Error>`.

```rust
pub enum DownloadError {
    Io { operation: &'static str, path: PathBuf, source: io::Error },
    Http(String),
    UnexpectedStatus { status: u16 },
    ChecksumMismatch { expected: String, actual: String },
    AlreadyInProgress { path: PathBuf },
    Cancelled,
    InvalidChecksum(String),
}
```

Перед возвратом ошибка пишется в `log::error!`.

## Настройка

`AppSettings.image_cache_path: PathBuf` под `#[serde(default)]`, чтобы
существующие `settings.toml` читались без миграции — тем же приёмом, что
`endpoint_id` и `network_mode` в `VmComputeSystemMapping`.

Голый `#[serde(default)]` для `PathBuf` даёт пустой путь, а не
`%LOCALAPPDATA%\VMLord\images`. Поэтому пустое значение достраивается в
`SettingsStore::load_or_create` из каталога конфигурации — тем же способом,
каким уже выводится `vm_storage_path`, и это заодно делает путь подменяемым в
тестах, где `LOCALAPPDATA` не определён.

`SettingsStore::save` создаёт каталог кеша так же, как создаёт каталог VM и
каталог логов.

## Логирование

Уровни DEBUG..ERROR, `TRACE` не используется.

* DEBUG — выбранный `CachePlan`, запрошенный и полученный диапазон, начало и
  конец хеширования.
* INFO — начало загрузки с URL и размером, попадание в кеш, успешное завершение.
* WARN — несовпадение суммы кешированного файла, игнорирование `Range` сервером,
  ответ 416.
* ERROR — любая возвращаемая ошибка.

## Тестирование

Чистые функции — прямыми unit-тестами: `resume_decision`, разбор
`Content-Range`, имя файла из URL и суммы, троттлинг с
`min_interval = Duration::ZERO`.

Сеть — интеграционными тестами на `std::net::TcpListener` в петле, отдающем
фикстурные байты. Трейта-заглушки над HTTP не будет: это ровно тот
single-implementation trait, который запрещает AGENTS.md, а живой сокет
проверяет и наш код, и поведение `ureq`. Сценарии:

* полная загрузка с нуля, сумма сходится;
* сервер отдаёт 206 на `Range` — докачка из `.part`;
* сервер игнорирует `Range` и отдаёт 200 — загрузка с начала;
* сервер отдаёт 416 — повторный запрос без `Range`;
* сервер обрывает соединение на середине — ошибка, `.part` сохранён;
* сервер отдаёт байты, не сходящиеся с суммой — `ChecksumMismatch`, `.part`
  усечён.

Кеш и гонки:

* попадание в кеш не ходит в сеть;
* кешированный файл с неверным содержимым удаляется и перекачивается;
* два потока на один URL — один качает, второй получает `AlreadyInProgress`;
* лок, отпущенный другим потоком, позволяет следующей попытке докачать `.part`;
* финальный файл, появившийся до переименования, принимается как чужая победа.

Прогресс:

* фазы приходят в порядке `Connecting → Downloading → Verifying → Completed`;
* последнее значение `Downloading` публикуется, несмотря на троттлинг;
* при попадании в кеш есть `Verifying`, но нет `Downloading`.

Отмена:

* флаг, взведённый посреди загрузки, даёт `Cancelled` и сохраняет `.part`.

Сеть в тестах — только петля. Тест на реальном образе из `VMLORD_TEST_CLOUD_IMAGE`
относится к #51 и здесь не заводится.
