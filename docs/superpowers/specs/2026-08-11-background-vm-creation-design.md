# TASK-64: фоновое создание VM, состояние Building и прогресс

Дизайн восьмой подзадачи эпика #3 «Provisioning Linux»: унести созданный в #61
конвейер в рабочий поток, показать строящуюся VM в списке со стадией и дать
сборку отменить. Предыдущая подзадача — #61; следующая — #65 (форма создания и
её кнопка отмены).

## Задача

`WorkspaceApp::create_vm` зовёт `HcsVmRepository::create_vm` прямо из
UI-потока eframe, а тот — `VmCreationPipeline::create`, внутри которого теперь
живут резолв релиза, скачивание образа на сотни мегабайт, проверка SHA-256 и
посекторная заливка в VHDX. Окно замирает на минуты, без единого признака
жизни; понятия прогресса нет ни в одном крейте, кроме `DownloadPhase`, который
#61 завёл и оставил без читателя.

В объём входит: рабочий поток на сборку, `VmState::Building` со стадией,
отмена, отказ остальных операций над строящейся VM, отчёт о неудаче в
диагностику и подстановка настоящих publisher'а и флага отмены в композиционном
корне.

Вне объёма: форма создания VM и кнопка отмены в ней (#65); консоль COM1 (#62);
ожидание готовности гостя (#63). UI здесь трогается ровно настолько, чтобы новое
состояние отображалось непротиворечиво.

## Слои

Поток принадлежит `platform` и живёт внутри `HcsVmRepository`. `create_vm`
принимает запрос и немедленно возвращает `Ok`, `list_vms` склеивает записи
`MetadataStore` со списком строящихся. `VmRepository` остаётся синхронным,
`WorkspaceApp` не меняется вовсе, а UI узнаёт о `Building` через свой уже
существующий секундный `refresh`.

Альтернатива — поток в `app` — отвергнута: тогда `WorkspaceApp` должен отдать
репозиторий потоку, то есть спрятать его за `Mutex` и потребовать `Send`. Это
сериализует `list_vms` с сборкой и просто переносит замирание на слой выше,
ничего не решая.

## Домен

`crates/core/src/progress.rs` получает стадию сборки и её снимок:

```rust
/// Which step of creating a VM is running.
pub enum BuildStep { Downloading, WritingDisk, Provisioning, Registering }

/// What creating a VM looks like from outside the worker thread.
pub struct BuildProgress {
    pub step: BuildStep,
    /// Only meaningful while `step` is `Downloading`.
    pub download: Option<DownloadPhase>,
}
```

`VmState` получает вариант `Building { progress: BuildProgress }`. Оба типа
`Copy`, так что `VmState` остаётся `Copy`, как сегодня.

Четыре стадии покрывают оба источника: `LocalMedia` проходит `WritingDisk`
(пустой VHDX) и `Registering`, `CloudImage` — все четыре. Общего процента по
конвейеру нет: это решение грилинга эпика, и знаменателя у такого процента всё
равно нет — скачивание, заливка и создание системы несоизмеримы.

Байты скачивания показываются, потому что `DownloadPhase` их уже несёт и
`fetch_image` их уже публикует. Не показать их значило бы держать самую долгую
стадию немой, имея готовый счётчик.

## Публикация прогресса

`ProgressPublisher` и `ProgressThrottle` становятся дженериками по `P: Copy`:
слот и троттлинг от содержимого не зависят, а держать их нужно теперь дважды —
под `DownloadPhase` и под `BuildStep`. Правка в `crates/image` механическая:
восемь сигнатур получают `<DownloadPhase>`; вызовы `ProgressPublisher::default()`
в тестах выводят параметр сами и не меняются.

Слота два, а не один, потому что байты пишутся глубоко внутри `fetch_image`, а
стадии — снаружи него. Один слот потребовал бы либо чтобы `crates/image` знал о
стадиях сборки VM, либо отдельного потока-пересыльщика. Оба хуже, чем сложить
два значения в момент чтения — тем более что `download` осмыслен ровно на одной
стадии.

Склейка и есть единственный новый тип — шов между сборкой и тем, кто на неё
смотрит:

```rust
/// The channel between a VM being built and the thread watching it: what the
/// build is doing, and whether it has been told to stop.
#[derive(Clone, Default)]
pub struct BuildMonitor {
    step: ProgressPublisher<BuildStep>,
    download: ProgressPublisher<DownloadPhase>,
    cancel: Arc<AtomicBool>,
}
```

Со стороны сборки — `report(step)`, `downloads()` и `cancel_flag()` для
передачи вглубь `vmlord-image`, `check_cancelled() -> Result<(),
RepositoryError>`. Со стороны наблюдателя — `cancel()` и `snapshot() ->
BuildProgress`, который и подставляет `download` только на `Downloading`.

`BuildMonitor` живёт в `core` рядом с `ProgressPublisher`: он не знает ни
файловой системы, ни Windows, а `platform`, `image` и композиционный корень
все трое им пользуются.

## Конвейер

`VmCreationPipeline::create` получает пятым параметром `&BuildMonitor` и
сообщает те стадии, которые выполняет сам: `WritingDisk` вокруг
`create_dynamic_vhdx` для `LocalMedia`, `Provisioning` вокруг ключей, хеша и
seed, `Registering` вокруг `config.json`, грантов, создания HCS-системы и
записи метаданных. Между стадиями стоит `monitor.check_cancelled()?`.

`CloudDiskImporter` получает монитор четвёртым аргументом:

```rust
pub type CloudDiskImporter = Box<
    dyn Fn(&CloudImage, u64, &Path, &BuildMonitor) -> Result<(), RepositoryError>
        + Send + Sync,
>;
```

Свои две стадии он объявляет сам — `Downloading` перед `open_cloud_image`,
`WritingDisk` перед `import_image`. Отчитывается тот, кто выполняет: скачивание
и заливка происходят внутри одного замыкания, и снаружи конвейер их не
различит.

Все boxed-замыкания конвейера получают `+ Send + Sync`, а репозиторий держит
`Arc<VmCreationPipeline>`, чтобы поток мог его позвать. Продакшн-замыкания
захватывают `PathBuf` и свободные функции, тестовые — `Arc<Mutex<Calls>>`;
ограничение выполняется всеми и ни одного не переписывает.

`import_image` получает `&AtomicBool` и проверяет отмену на границе чанков.
Это вторая по длине стадия, и не уметь её прервать означало бы, что отмена
ждёт конца заливки — то есть не работает.

## Отмена и падение

Флаг отмены взводится из трёх мест:

- пользователь — новый `cancel_create(&mut self, name: &str)` в
  `VmRepository`, с отказом по умолчанию, как у `open_display`. Вызывающий
  появится в #65, но метод заводится сейчас: без него репозиторий может
  отменять сборку, а домен об этом не знает, и #65 пришлось бы менять контракт
  ради кнопки. `delete_vm` отменой не подрабатывает — удалять то, чего ещё
  нет, значит смешивать две разные операции в одном имени;
- закрытие приложения — `Drop for HcsVmRepository` взводит все флаги и
  джойнит все потоки, как `Drop for DhcpService`. Без этого процесс уходит либо
  посреди записи в VHDX, либо в бесконечное ожидание;
- паника потока — страж на `Drop` внутри `create`, знающий каталог VM и
  созданную HCS-систему.

Отмена — обычная ошибка: `check_cancelled` возвращает `RepositoryError` с
текстом «creating the VM was cancelled», и дальше работает существующий
`rollback`. Отдельного пути очистки не заводится, иначе их станет два и они
разойдутся.

Страж заменяет нынешний ручной флаг `system_created`. На `Ok` и перед явным
`self.rollback(...)` он разоружается, поэтому текст ошибки по-прежнему
собирается вызовом, который умеет вложить в сообщение неудачу самой очистки.
Паника до этой точки стража не минует: он сносит HCS-систему и каталог VM
по пути наружу, записав в лог, что именно унёс. `catch_unwind` не годится —
замыкания швов не `UnwindSafe`, а `AssertUnwindSafe` утверждал бы ровно то,
что здесь и требуется доказать.

Осиротевшего HNS-endpoint при отмене не бывает: endpoint создаётся при первом
старте VM, а не при её создании — на всём пути `create` нет ни одного вызова
HNS. Пункт задачи про endpoint выполняется тем, что создавать здесь нечего.

## Реестр сборок

Новый модуль `crates/platform/src/build.rs` держит строящиеся VM по имени: на
каждую — `BuildMonitor`, поля будущей `VmSummary`, взятые из запроса, и
`JoinHandle`.

`create_vm`: валидация запроса, отказ по занятому имени — и в `MetadataStore`,
и в реестре, — отказ по существующему каталогу, затем запись в реестр и поток
с именем `vmlord-build-<имя>`. Всё, что может отказать дёшево и наверняка,
происходит до потока, чтобы очевидная ошибка возвращалась вызывающему как
ошибка, а не приезжала диагностикой через секунду.

Проверка имени расширяется на реестр не для удобства: без неё два запроса с
одним именем оба проходят проверку по стору и дерутся за один каталог.
Параллельные сборки при разных именах — разрешены.

Поток зовёт конвейер, пишет результат в общий буфер диагностик (`diagnostics`
становится `Arc<Mutex<Vec<Diagnostic>>>`) и помечает себя завершившимся.
Завершившиеся записи собираются и джойнятся в `take_diagnostics`: он `&mut
self`, вызывается на каждом refresh сразу после `list_vms`, и там уже живёт
ровно этот приём для освобождённых HCS-хендлов.

`list_vms` отдаёт строящиеся VM с `VmState::Building { progress:
monitor.snapshot() }`, RAM, дисками и ядрами из запроса и адресом `None`.
Неудавшаяся сборка откатывается, до `MetadataStore` не доходит и просто
исчезает из списка.

`start_vm`, `stop_vm`, `force_stop_vm`, `update_vm`, `delete_vm` и `open_ssh`
сначала смотрят в реестр и отказывают текстом «VM "dev" is still being
created». Платформа проверяет это независимо от `WorkspaceApp`: его список —
кэш, а решение по живой VM принимается там, где живёт реестр.

## Отчёт о неудаче

Отдельного видимого состояния «сборка провалилась» не заводится. Поток кладёт
`Diagnostic { level: Error, message: "Failed to create VM \"dev\": ..." }` в
буфер, `WorkspaceApp::refresh` его выгребает следом за `list_vms`, и текст
виден там же, где остальные ошибки. Строка VM при этом исчезает — сборка не
оставила ни каталога, ни метаданных, и показывать нечего.

## Композиционный корень

`cloud_disk_importer` перестаёт подставлять `ProgressPublisher::default()` и
`&AtomicBool::new(false)` и берёт их из монитора; комментарий про заглушки
уходит вместе с ними.

## UI

`crates/ui/src/lib.rs:1337` сегодня подписывает `VmState::Starting` как
«Building» — за неимением настоящего Building. Подпись чинится: `Starting` —
«Starting», `Building` — «Building» со стадией. Разборы состояния перестают
предлагать строящейся VM Start, Stop и Delete. Форма, кнопка отмены и показ
процентов — #65.

## Ошибки и логи

INFO — начало и конец сборки с именем VM; DEBUG — переход стадии; WARN —
отмена; ERROR — неудача сборки и всё, что не удалось убрать при откате.
Секреты в лог не попадают: сообщения несут имя VM и стадию, и правило #61
остаётся в силе.

## Тесты

`crates/core`:

- `snapshot` показывает байты только на `Downloading` и не тащит устаревшую
  фазу скачивания в следующую стадию;
- `cancel` виден через клон монитора, а `check_cancelled` даёт ошибку с
  названной причиной.

`crates/platform`, unit:

- сборка проходит стадии в объявленном порядке и исчезает из списка после
  успеха, оставив запись в метаданных;
- отмена посреди сборки не оставляет каталога VM и не оставляет записи в
  метаданных;
- паникующий конвейер тоже не оставляет каталога — страж отрабатывает на
  раскрутке стека;
- второе создание с занятым именем отбивается, пока первое ещё строится, и
  второго потока не заводит;
- `start_vm`, `delete_vm` и `open_ssh` над строящейся VM отказывают текстом,
  называющим VM, а не «not found»;
- `list_vms` показывает `Building` во время сборки и не показывает после;
- неудача сборки оставляет ровно одну диагностику уровня `Error` с именем VM.

`crates/platform/tests/hyperv.rs`, `#[ignore]`:

- создание VM из настоящего cloud-образа возвращает управление немедленно,
  стадии сменяются, и по завершении VM существует;
- отменённая на скачивании сборка не оставляет каталога.

Ручная проверка на живом Hyper-V — за владельцем проекта.

## Известные ограничения

Заливка в VHDX не сообщает байтов: счётчика там нет, а заводить его — это
публикация из `copy_image`, то есть новый параметр в модуле, который сейчас
занят только корректностью записи. Стадия остаётся грубой, как и решено
грилингом.

Сборка не переживает перезапуск приложения: `Drop` её отменяет и откатывает.
Возобновляемая сборка потребовала бы состояния на диске и разбора недоделанных
каталогов при старте — это заметно больше, чем стоит первая версия.
