# TASK-55: пара ключей ed25519 на VM

Дизайн генерации и хранения SSH-ключа виртуальной машины: своя пара ed25519 на
каждую VM, приватная половина — в каталоге VM с ужатым ACL, публичная —
наготове для `ssh_authorized_keys` в cloud-config. Подзадача эпика #3
«Provisioning Linux», идёт после контракта (#57) и до сборки seed в конвейере.

## Задача

AppSandbox держит один общий ключ на все песочницы —
`%ProgramData%\AppSandbox\ssh\id_appsandbox` (`legacy-backend/src/windows.rs:691`).
Компрометация одной VM даёт доступ ко всем остальным. Решение грилинга по эпику:
своя пара на каждую VM.

В объём входят: генерация пары ed25519, сериализация в OpenSSH-формат, запись
приватного ключа в каталог VM с ограниченным DACL, чтение публичного ключа
обратно, удаление ключа вместе с VM.

Вне объёма: вызов из `VmCreationPipeline` и попадание публичного ключа в
user-data — это #58 и сборка seed в конвейере; решение «генерировать или нет» по
`SshAccess::Enabled { deploy_key }` принимает вызывающий, а не эти модули.

## Ключевое решение: генерация отдельно от хранения

Генерация пары портируема и проверяема где угодно. «Приватный ключ с
ограниченным ACL» — это Win32 и `unsafe`, то есть `crates/platform`, который вне
Windows не собирается.

Поэтому два места:

* `crates/keys` (пакет `vmlord-keys`) — чистая генерация и OpenSSH-сериализация.
  Тесты «генерация / формат / соответствие пары», которых задача требует
  явно, гоняются на любой платформе.
* `platform::vm_key` — файлы и права. Узкий интерфейс, который конвейеру в #59
  будет легко подделать, как уже подделываются `vhd_creator` и `access_granter`.

Третий вариант — генерация в `core` — отпадает: `core` это домен, там нет и не
должно быть криптографии.

## `crates/keys`

```rust
pub struct VmKeyPair { /* приватные поля */ }

pub fn generate(vm_name: &str) -> Result<VmKeyPair, RepositoryError>;

impl VmKeyPair {
    pub fn private_openssh(&self) -> &str;
    pub fn public_openssh(&self) -> &str;
}
```

Зависимости: `ssh-key` 0.7 (Apache-2.0/MIT, синхронный, OpenSSH-формат), `log`,
`vmlord-core` — ради `RepositoryError`. Свой тип ошибки не заводится:
единственная возможная неудача — `ssh-key` не смог сериализовать ключ — всё
равно едет наверх в этой форме, и лишняя конверсия в `platform` ничего не
добавляет. Точный состав фич `ssh-key` (`ed25519`, генерация, источник
случайности) закрепляется компиляцией на первом шаге плана: в 0.x он менялся от
версии к версии.

Приватный ключ — OpenSSH PEM, LF, **без passphrase**. Это осознанно: VMLord
подключается к гостю сам, без интерактива, а парольная фраза, лежащая рядом с
ключом, не защищает ни от чего. Защита — DACL файла.

Публичный ключ — строка вида `ssh-ed25519 AAAA… vmlord@<vm_name>`. Комментарий
занимает хвост строки `authorized_keys`, поэтому управляющие символы из имени VM
вырезаются: перевод строки в комментарии — не опечатка, а вторая запись в файле.

`Debug` не реализуется вовсе — ни для `VmKeyPair`, ни производный. Приватный
ключ не должен уметь напечататься; это тот же приём, которым `Password` в `core`
защищена от `{:?}` на месте вызова. Строка приватного ключа хранится в
`Zeroizing`, который `ssh-key` и так возвращает.

## `platform::vm_key`

```rust
pub(crate) fn write(vm_directory: &Path, pair: &VmKeyPair) -> Result<(), RepositoryError>;
pub(crate) fn read_public(vm_directory: &Path) -> Result<Option<String>, RepositoryError>;
```

Пути даёт `layout`: `ssh_key_path` → `<vm>/keys/id_ed25519`,
`ssh_public_key_path` → `<vm>/keys/id_ed25519.pub`. Публичный файл на диске не
необходимость — публичная половина выводится из приватной за микросекунды, — а
удобство: человек должен видеть, какой ключ уехал в гостя, не запуская VM.

### Порядок записи

`create_dir_all` на `keys/`; `File::create_new` на `id_ed25519`; **сразу** ужать
DACL; и только потом записать байты. Между созданием файла и
`SetNamedSecurityInfoW` есть окно, в котором файл лежит с унаследованными
правами, — в это окно должен попадать пустой файл, а не ключ. Публичный файл
пишется обычным `fs::write`, права ему не ужимаются.

### DACL

Наследование отключается, список выставляется явно: `SYSTEM`, `Administrators` и
SID пользователя, от имени которого работает VMLord —
`D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;<SID>)`. SID берётся из
`OpenProcessToken` + `GetTokenInformation(TokenUser)`; он же ставится владельцем
файла. Вызов — `SetNamedSecurityInfoW` с
`DACL_SECURITY_INFORMATION | PROTECTED_DACL_SECURITY_INFORMATION | OWNER_SECURITY_INFORMATION`.

Пользователь в списке нужен, а не является послаблением. Без него
`ssh -i <path>` из обычной, неповышенной консоли упирается в access denied:
неповышенный токен администратора не несёт группу `Administrators`, — а ключ
существует ровно затем, чтобы им заходили руками. Это же ровно та форма ACL,
которую требует Win32-OpenSSH: он отказывается брать ключ, чей DACL шире, чем
владелец плюс SYSTEM и Administrators.

### Ошибки

* Ключ уже есть — `create_new` даёт `AlreadyExists`, наружу идёт «VM "x" already
  has an SSH key». Не тихая перезапись: гость с уже розданным ключом остался бы
  с ключом, к которому у хоста нет пары. Пересоздание — это удалить VM и создать
  заново.
* Ужать DACL не удалось — ошибка, а не предупреждение. Файл уже создан, и
  оставить приватный ключ с унаследованными правами хуже, чем провалить
  создание. `write` убирает за собой `keys/` и возвращает ошибку.
* `read_public` на отсутствующем файле возвращает `Ok(None)`. VM без ключа —
  нормальное состояние (`ssh_enabled: false`), а не сбой.

### Удаление

Отдельного кода не требуется: `cleanup::remove_vm_directory` уносит каталог
целиком через `remove_dir_all`. Требование задачи закрывается тестом, который
это фиксирует.

## Логирование

DEBUG — «сгенерирована пара ed25519 для VM "x"», «DACL на … ужат до SYSTEM,
Administrators, \<user\>», «у VM "x" нет SSH-ключа». ERROR — на каждой из
перечисленных выше неудач. Ни байта приватного ключа в строках нет; публичный
тоже не печатается целиком — только факт его наличия. TRACE не используется.

## Тестирование

`crates/keys`, на любой платформе:

* сгенерированный приватный ключ читается обратно `PrivateKey::from_openssh`;
* публичный ключ читается `PublicKey::from_openssh`, алгоритм — ed25519;
* публичная половина, выведенная из приватного ключа, совпадает с той, что
  отдана наружу, — это и есть «соответствие пары»;
* два вызова `generate` дают разные ключи;
* комментарий содержит имя VM, а управляющие символы из имени в него не
  попадают;
* приватный ключ не появляется в выводе форматирования.

`crates/platform`, на Windows, во временном каталоге и без Hyper-V:

* `write` создаёт оба файла, содержимое совпадает с переданным;
* повторный `write` в тот же каталог отказывает и не портит существующий ключ;
* `read_public` возвращает записанное, а на пустом каталоге — `None`;
* DACL приватного файла, прочитанный обратно `GetNamedSecurityInfoW`, защищён от
  наследования и содержит ровно три разрешающих записи;
* `remove_vm_directory` уносит `keys/` вместе с каталогом VM.

## Критерий выхода

`cargo test` зелёный; приватный ключ существует только в файле с ужатым DACL и
не встречается ни в логах, ни в метаданных; `vmlord-keys` собирается и
тестируется без Windows.
