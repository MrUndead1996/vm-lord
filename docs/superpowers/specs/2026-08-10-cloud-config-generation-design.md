# TASK-58: генерация cloud-config (user-data, meta-data)

Дизайн генератора документов NoCloud: как контракт провизионинга из #57
превращается в два текстовых документа, которые cloud-init читает внутри гостя.
Пятая подзадача эпика #3 «Provisioning Linux». Следом идёт #59 — ISO9660-writer,
который эти две строки кладёт в том с меткой `CIDATA`, и #61 — сборка seed в
конвейере создания VM.

## Задача

`Provisioning` (`crates/core/src/provisioning.rs:46`) описывает, что VMLord
обещает донести до гостя: пользователь, пароль, SSH, `locale`, `keyboard`,
`timezone`. Донести это некому: нативный путь создаёт VM без единого документа
конфигурации.

В объём входят два документа и правила их печати. Вне объёма — хеш пароля (#56),
пара ключей ed25519 (#55), запись ISO (#59), подключение seed к VM (#61) и всё
Windows-специфичное.

## Крейт

Новый крейт `crates/seed` (`vmlord-seed`). Генерация документов — работа со
строками: ни Windows API, ни файловой системы, ни сети, и тесты гоняются на
хосте, а не кросс-компиляцией. Зависимости: `log` и `vmlord-core` (ради
`SshAccess`), в dev — `serde_yaml_ng`.

Крейт назван по артефакту, а не по формату, потому что #59 кладёт туда же
ISO9660-writer: обе половины seed — чистые байты, симметрично `crates/image`,
где живут внешние форматы (qcow2, `SHA256SUMS`) отдельно от домена и от
платформы.

Модули: `user_data`, `meta_data`, `scalar` (экранирование), `lib` (вход и типы).

## Вход

```rust
pub struct SeedRequest<'a> {
    pub vm_name: &'a str,
    pub instance_id: &'a str,
    pub username: &'a str,
    /// $6$-хеш из #56. `None` означает вход только по ключу.
    pub password_hash: Option<&'a str>,
    /// Публичный ключ из #55, в формате `authorized_keys`.
    pub authorized_key: Option<&'a str>,
    pub ssh: SshAccess,
    pub locale: &'a str,
    pub keyboard: &'a str,
    pub timezone: &'a str,
    /// `admin_group` профиля: `sudo` в Debian-семействе, `wheel` в Fedora.
    pub admin_group: &'a str,
    /// Юниты SSH-демона из профиля, для случая выключенного SSH.
    pub ssh_units: &'a [String],
}

pub struct Seed {
    pub user_data: String,
    pub meta_data: String,
}

pub fn build(request: &SeedRequest<'_>) -> Seed;
```

Поля плоские, а не ссылка на `Provisioning`, ровно ради одного свойства:
plaintext-пароль в крейт не попадает вообще. Тест «в документе нет пароля»
тогда проверяет не удачное стечение обстоятельств, а факт, обеспеченный типом —
`Password` в `seed` попросту не виден.

`instance_id` — строка, а не `Uuid`: форматирует её вызывающий в #61, где `uuid`
уже есть, и крейт остаётся без этой зависимости.

Функция инфалибельна, `Result` не возвращает. Всё, что могло бы её сломать —
управляющие символы в значениях — отсечено `Provisioning::validate()`, а всё
остальное представимо после экранирования (ниже). Ввод-вывод, а с ним и ошибки,
появятся в #59.

## user-data

Пользователь `dev` с паролем, ключом и включённым SSH:

```yaml
#cloud-config
users:
  - name: 'dev'
    shell: '/bin/bash'
    groups: ['sudo']
    sudo: 'ALL=(ALL) NOPASSWD:ALL'
    lock_passwd: false
    hashed_passwd: '$6$rounds=...'
    ssh_authorized_keys:
      - 'ssh-ed25519 AAAA... vmlord'
ssh_pwauth: true
locale: 'en_US.UTF-8'
timezone: 'Europe/Moscow'
write_files:
  - path: '/etc/default/keyboard'
    permissions: '0644'
    content: |
      XKBMODEL="pc105"
      XKBLAYOUT="us"
      XKBVARIANT=""
      XKBOPTIONS=""
      BACKSPACE="guess"
growpart:
  mode: auto
  devices: ['/']
resize_rootfs: true
```

Первая строка `#cloud-config` обязательна: по ней cloud-init опознаёт формат. Для
YAML это комментарий, поэтому ни один парсер её не проверит — только байтовое
сравнение.

Что меняется от входа:

| Вход | Документ |
| --- | --- |
| `password_hash: None` | нет `hashed_passwd`, `lock_passwd: true` |
| `password_hash: Some` | `hashed_passwd`, `lock_passwd: false` |
| `authorized_key: None` | нет `ssh_authorized_keys` |
| SSH включён и хеш задан | `ssh_pwauth: true` |
| иначе | `ssh_pwauth: false` |
| `SshAccess::Disabled` | `runcmd` с `['systemctl', 'disable', '--now', <ssh_units>]` |

`sudo` — всегда `ALL=(ALL) NOPASSWD:ALL`. Правило пишет сам cloud-init в
`/etc/sudoers.d/90-cloud-init-users`, поэтому различие `sudo`/`wheel` на права не
влияет; членство в `admin_group` прописывается отдельно, потому что его ожидают и
`sudo -l`, и человек, заглянувший в `id`. `NOPASSWD` безусловен: при входе только
по ключу пароля, который спросил бы sudo, не существует, а Ubuntu ровно так же
настраивает собственного пользователя `ubuntu` в своих облачных образах.

`SshAccess::Disabled` не молчание, а действие: в облачном образе демон SSH уже
установлен и включён, и документ, который его не трогает, оставил бы выбор
пользователя без последствий. Имена юнитов различаются между дистрибутивами
(`ssh.socket`/`ssh.service` против `sshd.service`), поэтому они данные профиля, а
не литерал в генераторе: `DistroProfile` получает поле `ssh_units: Vec<String>`,
для Ubuntu — `["ssh.socket", "ssh.service"]`. Лишний юнит на релизе без
socket-активации даёт ненулевой код возврата, который `runcmd` не считает
фатальным.

`growpart` и `resize_rootfs` печатаются явно, хотя таковы и умолчания cloud-init:
рост rootfs до `disk_gb` — обещание VMLord, и оно должно быть видно в документе, а
не зависеть от версии.

## meta-data

```yaml
instance-id: 'vmlord-4f1c...'
local-hostname: 'my-vm'
```

`instance-id` из `vm_id`, потому что тот неизменен всю жизнь VM. Seed остаётся
прицепленным постоянно, cloud-init перечитывает его на каждом бусте и по
совпадению `instance-id` не повторяет per-instance модули — решение эпика.

`local-hostname` — имя VM как есть. Форму имени под hostname сегодня проверяет UI
(`crates/ui/src/lib.rs:788`), домен требует лишь непустоты; генератор имя не
чинит, а печатает в кавычках. Перенос правила в домен — #65.

## Экранирование

Два разных места с двумя разными правилами, и это не небрежность, а разница
читателей.

**YAML.** Каждый пришедший извне скаляр печатается одинарно-кавычным скаляром с
удвоением апострофа (`don't` → `'don''t'`). В таком скаляре нет ни одной
escape-последовательности: спецсимволы значения не имеют, и значение не может
выйти за пределы своего узла. Литералы структуры документа (`true`, `false`,
`auto`) кавычек не получают — они и есть типы, которые cloud-init различает.

**Шелл.** Содержимое `/etc/default/keyboard` читается шелл-скриптами через
`source`, поэтому значение внутри двойных кавычек экранируется по правилам шелла
(`\`, `"`, `` ` ``, `$`). Раскладка вида `us$(...)` иначе стала бы подстановкой
при чтении файла — YAML-кавычки от этого не защищают, потому что читатель здесь
не YAML.

## Секреты

В крейт приходит только `$6$`-хеш; plaintext-пароль и приватный ключ не приходят
никогда. `Seed` не реализует `Debug`: документ содержит хеш, а хеш незачем
печатать в лог. Логирование — `log::debug!` со сводкой без значений: имя
пользователя, есть ли хеш, есть ли ключ, состояние SSH.

## Ограничение

`/etc/default/keyboard` — путь Debian-семейства; в Fedora это `/etc/vconsole.conf`
с другими ключами. Там понадобится не другое значение поля, а другой механизм —
например, штатный модуль `keyboard` cloud-init поверх `localectl`. Раскладка —
единственное такое место: `users`, `ssh_pwauth`, `locale`, `timezone`, `growpart`
и `resize_rootfs` работают на любом дистрибутиве. Абстракция «диалект документа»
сегодня была бы абстракцией без второго пользователя; когда появится второй
дистрибутив, правка будет в одном известном месте.

## Тесты

Продакшн печатает документ вручную, тесты читают его `serde_yaml_ng` 0.10 и
проверяют значения по ключам — не байты. Так тест переживает правку отступа и не
переживает изменение смысла, а читает документ той же оптикой, что и PyYAML внутри
cloud-init.

Байтовыми остаются два утверждения, которых парсер по определению не увидит:
первая строка ровно `#cloud-config`, и в документе нет ни plaintext-пароля, ни
приватного ключа.

По строке таблицы «вход → документ» на каждый случай; отдельно — значение с
апострофом в `locale` и раскладка с `$` и `"`: первый разбирается обратно в
исходную строку, вторая приезжает в `/etc/default/keyboard` экранированной.
`meta-data` — оба ключа. `admin_group: "wheel"` проверяет, что группа взята из
данных, а не из литерала.

Сборка — `cargo build --target=x86_64-pc-windows-gnu`, тесты `seed` и `core`
гоняются на хосте.
