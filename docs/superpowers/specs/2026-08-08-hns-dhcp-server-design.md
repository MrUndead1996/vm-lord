# TASK-47: встроенный DHCP-сервер для NAT Linux VM

Дизайн DHCP-сервера, выдающего Linux-гостю ровно тот адрес, который HNS уже
назначил его endpoint'у. Часть декомпозиции эпика #5 «Миграция HNS: базовая
сетевая интеграция»; опирается на #41 (endpoint виртуальной машины), #38
(подключение endpoint'а при старте) и #46 (освобождение endpoint'а при
остановке), все три уже в `main`.

## Задача

Спайк #40 показал: Linux-гость шлёт DHCP Discover/Request через HNS endpoint, но
HNS NAT не отвечает ни Offer, ни ACK. `EnableDhcpServer` для этой NAT-сети HNS
отвергает как unsupported. Сторонний DHCP-сервер на host vNIC подтверждён как
рабочее решение, и его роль занимает VMLord.

Адреса при этом продолжает раздавать HNS IPAM. DHCP-сервер VMLord — не
аллокатор: он только повторяет гостю то, что HNS уже решило, и не заводит
второго источника адресов, который разошёлся бы с первым.

## Что делает AppSandbox

Ничего, что можно позаимствовать: в поставке `third_party/appsandbox` только
бинарники, исходников DHCP там нет, а сетевая модель у него принципиально
другая. AppSandbox пересоздаёт endpoint на каждый старт и задаёт адрес явным
`IpConfigurations` (см. разбор в дизайне #46). Для Windows-контейнеров такой
записи достаточно, потому что HNS конфигурирует стек внутри. Hyper-V VM с
Linux-гостем адрес из `IpConfigurations` не видит: это конфигурация хостовой
половины endpoint'а, а гость по-прежнему остаётся с неподнятым интерфейсом,
пока кто-нибудь не ответит ему по DHCP.

## Выбор библиотеки

Задача называла `dhcplease`. Разбор исходников обеих кандидатур привёл к
`arcbox-dhcp` 0.6.3:

| | `dhcplease` 0.2.1 | `arcbox-dhcp` 0.6.3 |
|---|---|---|
| Зависимости | tokio (full), clap, chrono, socket2, tracing, serde | thiserror, tracing |
| Транспорт | владеет сокетом, бинд :67, async `run()` | нет: `handle_packet(&[u8]) -> Option<Vec<u8>>` |
| Привязки MAC→IP | `static_bindings` заморожены в `Arc<Config>` на `new()` | `reserve_ip` / `remove_reservation` в рантайме |
| Хранение lease | пишет `leases.json` | только в памяти |

Решающих доводов два. Первый: endpoint'ы создаются лениво, при первом старте
каждой VM, а у `dhcplease` набор привязок неизменен после конструктора — новая
VM потребовала бы пересоздания сервера и повторного бинда UDP 67 на каждом
старте. Второй: `arcbox-dhcp` не владеет транспортом, поэтому решение
проверяется юнит-тестами по байтам, без живого сокета, и в workspace не
появляется async-рантайм, которого там сейчас нет вовсе.

MSRV `arcbox-dhcp` — 1.96, тулчейн проекта — 1.97.1.

Отвергнуто: `dhcplease` как чистый кодек (тянет tokio full и clap ради
парсера) и собственный парсер DHCP (лишний код там, где готовый крейт
подходит целиком).

## Решения

### VMLord не аллокатор: фильтр до `handle_packet`

`arcbox_dhcp::DhcpServer` — полноценный сервер с пулом: `handle_discover` для
незнакомого MAC берёт свободный адрес из пула и заводит lease. Пул нужен, потому
что `reserve_ip` паникует на адресе вне `pool_start..pool_end`, так что диапазон
обязан покрывать host-часть подсети.

Поэтому пакет проходит проверку до того, как его увидит `arcbox`:

```
recv_from -> DhcpPacket::parse -> client_mac()
  MAC не в карте резерваций -> log::debug, пакет отброшен
  иначе                     -> server.handle_packet(bytes)
```

Проверка стоит именно на приёме, а не перед отправкой ответа, по двум причинам.
Сокет приходится держать на `0.0.0.0:67` — на Windows сокет, привязанный к
unicast-адресу vNIC, широковещательные Discover не получает, — и до него доходят
DHCP-броадкасты со всех интерфейсов хоста, включая обычную LAN. Фильтр на приёме
означает, что чужой клиент не получит ни Offer, ни NAK (NAK сорвал бы ему
настройку), и что состояние `arcbox` не пачкается чужими lease и занятыми
адресами. Второе важнее, чем кажется: занятый посторонним адрес позже уронил бы
`reserve_ip` паникой, когда HNS назначит этот адрес новому endpoint'у.

Так выполняются сразу два требования задачи: ответы ограничены сетью VMLord, и
ни один адрес мимо HNS IPAM выдан быть не может.

### Резервации: единственная точка вызова `reserve_ip`

`reserve_ip` паникует дважды — на адресе вне пула и на адресе, уже занятом в
аллокаторе, — а поле `allocator` у `DhcpServer` приватное, спросить
`is_available` снаружи нельзя. Значит, состояние аллокатора нужно знать самим.
`DhcpService` ведёт свою карту `HashMap<[u8; 6], Ipv4Addr>`, и `reserve` —
идемпотентный диф:

* пара `(mac, ip)` уже есть — ничего не делать;
* за `mac` числится другой адрес — `remove_reservation(mac)`, затем `reserve_ip`;
* адрес числится за другим MAC (endpoint пересоздан по #46; VM удалена и HNS
  переиспользовал адрес) — сначала `remove_reservation(другой_mac)`.

Инвариант: `reserve_ip` вызывается только на заведомо свободном адресе. Оба
`assert!`-а недостижимы конструктивно, а не по договорённости.

### Один экземпляр, создаётся при первом старте NAT VM

Сервер поднимается в `VmStartPipeline` после `HcnNetwork::ensure` и создания
endpoint'а, но до запуска compute system — как и требует задача, до старта
первой NAT VM. Раньше нельзя: `DhcpConfig` требует подсеть, а она известна
только когда HNS-сеть существует. При старте приложения поднимать сервер
отвергнуто: это создавало бы NAT-сеть и vEthernet-адаптер на хосте и занимало
UDP 67 у тех, кто NAT не пользуется вовсе.

При создании резервации засеваются по **всем** endpoint'ам, записанным в
`MetadataStore`, а не только по стартующей VM. Иначе после перезапуска VMLord
уже работающие гости не смогли бы продлить lease: сервер не знал бы их MAC и
отбросил бы их Request на приёме.

Дальше экземпляр живёт до конца процесса, и каждый следующий старт только
вызывает `reserve`.

### Подсеть, шлюз и DNS

Подсеть выводится из `EndpointAddress` (IP и `prefix_length`), который уже
читается в `hcn_endpoint.rs`: netmask из префикса, gateway — первый адрес
подсети, ровно как его определяет `Ipv4Subnet::gateway`, пул — host-диапазон.
Отдельного запроса свойств сети к HNS не нужно.

DNS шлюзом быть не может: WinNAT не держит DNS-прокси на адресе
`vEthernet (VMLord)`, и гость с таким сервером не разрешил бы ни одного имени.
Выдаются IPv4-серверы самого хоста, прочитанные через `GetAdaptersAddresses`, с
отбрасыванием loopback, link-local и адресов подсети VMLord; если пригодных не
осталось — 1.1.1.1 и 8.8.8.8. Гость видит те же имена, что и хост, включая
корпоративные зоны.

Lease — 24 часа. Сервер умирает вместе с процессом VMLord, и длинный lease
означает, что гость переживёт закрытие приложения и попробует renew заметно
позже. Опции 58/59 `arcbox-dhcp` не пишет, так что клиент возьмёт свои
умолчания: T1 = 0.5, T2 = 0.875 от срока.

### Занятый UDP 67 диагностируется, а не обходится

`SO_REUSEADDR` намеренно не ставится. На Windows он позволяет перехватить уже
занятый порт, и два DHCP-сервера на одном хосте отвечали бы вперемешку. Отказ
бинда превращается в диагностику, различающую занятый порт (ICS, Hyper-V Default
Switch, сторонний сервер), отказ firewall и недостаток прав.

Отказ поднятия сервера — это отказ `start_vm`, а не тихий старт VM без сети: то
же решение, что уже принято эпиком для сети и endpoint'а.

### Ответ уходит броадкастом, пока у гостя нет адреса

Адресат ответа выбирается по `ciaddr`: если гость уже имеет адрес (renew) —
unicast на `ciaddr:68`, иначе broadcast на `255.255.255.255:68`. Гостю без
адреса unicast доставить нечем: ARP-запись за нас никто не создаст.

## Реализация

### `crates/platform/src/dhcp.rs`

Новый модуль, единственный владелец сокета и `arcbox_dhcp::DhcpServer`:

```rust
pub(crate) struct DhcpService { /* поток, флаг остановки, Arc<Mutex<State>> */ }

struct State {
    server: arcbox_dhcp::DhcpServer,
    reserved: HashMap<[u8; 6], Ipv4Addr>,
}

impl DhcpService {
    fn start(subnet: Ipv4Subnet, dns: Vec<Ipv4Addr>) -> Result<Self, RepositoryError>;
    fn reserve(&self, mac: [u8; 6], ip: Ipv4Addr) -> Result<(), RepositoryError>;
}
```

Поток читает сокет с `set_read_timeout`, чтобы замечать флаг остановки; `Drop`
сигналит и делает join. Никаких глобальных статиков: экземпляр держит замыкание
в `VmStartPipeline`.

### Шов в `VmStartPipeline` (`start.rs`)

`VmNetworkAdapter` дополняется адресом endpoint'а, рядом с уже имеющимися
`access_granter` / `system_starter` / `endpoint_provider` появляется четвёртый
инжектируемый шаг:

```rust
type DhcpRegistrar =
    Box<dyn Fn(&str /* mac */, &EndpointAddress) -> Result<(), RepositoryError>>;
```

Продакшн-реализация лениво поднимает `DhcpService`, засевает резервации по
`MetadataStore` и вызывает `reserve`. Тесты подставляют записывающую заглушку —
тем же способом, что и для остальных трёх шагов.

## Тестирование

Unit-тесты:

* диф резерваций: повтор той же пары, смена адреса у MAC, переезд адреса к
  другому MAC, новая пара;
* вывод netmask, gateway и границ пула из `EndpointAddress`;
* разбор MAC из формата, в котором его сообщает HNS, в `[u8; 6]`;
* выбор адресата ответа: `ciaddr` задан — unicast, нулевой — broadcast;
* пакет с незнакомым MAC не доходит до `handle_packet` и не меняет состояние;
* сквозь `arcbox` на синтетических байтах: Discover получает Offer именно с
  адресом HNS; Request на устаревший адрес после пересоздания endpoint'а
  получает NAK; Request на свой адрес получает ACK;
* DNS: loopback, link-local и адреса подсети VMLord отбрасываются, пустой
  результат даёт публичные серверы.

`#[ignore]`-тест в `crates/platform/tests/hyperv.rs`: старт Linux-гостя на живом
Hyper-V, ожидание адреса, проверка, что полученный гостем адрес совпадает с
адресом endpoint'а по данным HNS.

## Документация

`ARCHITECTURE.md` получает раздел про DHCP: почему HNS NAT не отвечает гостю,
почему VMLord не аллокатор, почему фильтр по MAC стоит на приёме, откуда берутся
шлюз и DNS, и явная фиксация — после закрытия VMLord renew никто не обслуживает,
гость доживает на выданном lease.

## Вне объёма

* **Перенос DHCP в Windows service или в tray**, чтобы lease продлевался без
  открытого UI, — будущее улучшение, названное в самой задаче.
* **Очистка endpoint'ов** при удалении VM и при `initialize` — #42. До неё
  резервация удалённой VM живёт до конца процесса; переезд её адреса к новому
  endpoint'у уже обработан дифом резерваций.
* **`VmSummary.ip_address`** — #37.
* **IPv6, опции 58/59, MTU и domain name** — гостю не нужны, `arcbox-dhcp` их
  не пишет.
