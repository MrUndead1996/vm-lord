# TASK-38: подключение HNS endpoint при старте VM

Дизайн интеграции сетевого endpoint'а в `VmStartPipeline`. Часть декомпозиции
эпика #5 «Миграция HNS: базовая сетевая интеграция»; опирается на #43 (общая
NAT-сеть) и #41 (endpoint виртуальной машины), обе уже в `main`.

## Задача

VM создаёт endpoint при первом старте и подключает его к себе. Сегодня
`VmStartPipeline` о сети не знает вовсе: он читает `config.json`, выдаёт доступ
к вложениям и стартует компьют-систему. Документ конфигурации не содержит
секции `NetworkAdapters`, а `VmComputeSystemMapping::endpoint_id` (#41) никто не
заполняет.

## Решения

### Что записывается в NetworkAdapters

Запись содержит `EndpointId` и `MacAddress`:

```json
"NetworkAdapters": {
  "3F2B0C11-...": { "EndpointId": "3F2B0C11-...", "MacAddress": "00-15-5D-01-02-03" }
}
```

MAC назначает HNS при создании endpoint'а; VMLord его читает, а не выбирает.
Так делает hcsshim, и так конфигурация заведомо полна — вариант «только
EndpointId» держится на предположении, что HCS достанет MAC из HNS сам.

Ключ записи — идентификатор endpoint'а. Он уникален, стабилен между стартами и
уже под рукой, так что отдельный NIC-идентификатор изобретать не нужно.

Чтение MAC требует `HcnQueryEndpointProperties`. Это кусок работы #37
(`VmSummary.ip_address`), вытянутый вперёд ради одного поля; сам адрес гостя
здесь не читается.

### Кому подключается endpoint

`VmComputeSystemMapping` получает поле `network_mode` под `#[serde(default)]`.
`VmCreationPipeline` записывает в него режим из запроса, `VmStartPipeline`
подключает endpoint только при `NetworkMode::Nat`. Старые mapping'и читаются как
`None` и остаются без сети — миграции не нужно.

Альтернатива «подключать всем безусловно, а условие добавить в #44» отклонена:
до #44 все VM создаются с `NetworkMode::None`, и такая VM получила бы NAT-адаптер
вопреки заявленному режиму.

Пока #44 не снял запрет на `NetworkMode::Nat` в `create_vm`/`update_vm`, ветка с
подключением endpoint'а достижима только из тестов. Это осознанная цена
корректности: #44 идёт следом и включает её одним изменением границы домена.

### Где проходит шов для тестов

`VmStartPipeline` получает третью инъектируемую зависимость — провайдер
endpoint'а:

```rust
Fn(&str /* vm_name */, Option<Uuid> /* записанный id */) -> Result<VmNetworkAdapter>
```

Шов проходит по операциям HNS, а не выше: «создать, только если endpoint'а нет»
и запись `endpoint_id` в `MetadataStore` остаются в пайплайне и покрываются
unit-тестами. Продакшн-реализация делает `HcnNetwork::ensure()` →
`HcnEndpoint::open_if_present(записанный id)` → при отсутствии `create` с новым
`Uuid` → `mac_address()`.

`open_if_present` перед каждым стартом — защита от endpoint'а, удалённого
снаружи или потерянного при сбросе HNS. Стоит один вызов и повторяет логику
`HcsSystem::open_if_present`.

### Порядок шагов старта

1. найти mapping;
2. при `NetworkMode::Nat` — получить endpoint (сначала сеть, потом endpoint);
3. если идентификатор новый — записать `endpoint_id` в mapping;
4. прочитать `config.json`, переписать секцию `NetworkAdapters`, записать файл
   обратно, если документ изменился;
5. выдать доступ к вложениям;
6. стартовать компьют-систему обновлённым документом.

Порядок вынужденный: секцию нельзя написать до того, как известны id и MAC, а
файл нужно обновить до старта — `start_hcs_system` пересоздаёт из этого
документа компьют-систему, которую HCS забыл.

Отказ на шагах 2–4 — это отказ `start_vm`, а не тихий старт без сети.

### Что происходит при неудаче

Endpoint при неудачном старте не удаляется и `endpoint_id` из mapping'а не
вычищается: endpoint переживает остановки и живёт до удаления VM, иначе гость
получал бы новый адрес после каждого сбоя.

Если endpoint создан, а запись в `MetadataStore` не удалась, остаётся сирота.
Она не удаляется здесь — собирать сирот будет `initialize` из #42, ровно как
описано в комментарии к `HcnEndpoint::create`.

### Переписывание config.json

`hcs_config::apply_network_adapter` — тот же приём, что уже используется для
`SizeInMB`/`Count` в `apply_topology`: разбор в `serde_json::Value`, точечная
правка, сериализация обратно. Весь остальной документ сохраняется: диски,
вложения и идентичность HCS должны пережить правку, а пересобрать документ с
нуля можно только тем состоянием, которое было у создания.

Отличие от `apply_topology`: секции ещё нет, поэтому ключ вставляется в
`/VirtualMachine/Devices`, а не правится существующий указатель. Отсутствие
самого `Devices` — ошибка. Секция перезаписывается целиком, так что повторный
старт сходится к тому же документу.

## Тестирование

Unit-тесты на `apply_network_adapter`: секция создаётся; ничего вне неё не
меняется; повторное применение даёт тот же документ; документ без
`/VirtualMachine/Devices` отклоняется; невалидный JSON отклоняется.

Unit-тесты на `VmStartPipeline`: порядок шагов; записанный `endpoint_id`
переиспользуется, а не создаётся заново; новый идентификатор попадает в store;
отказ провайдера обрывает старт до grant'ов и до старта; неудачный старт
оставляет `endpoint_id` на месте; VM с `NetworkMode::None` стартует без
обращения к провайдеру и без секции `NetworkAdapters`.

`#[ignore]`-тест в `crates/platform/tests/hyperv.rs` на реальном HNS. Ручная
parity-проверка на Hyper-V — за владельцем проекта.

## Вне объёма

* **Hot-detach адаптера** — ждёт спайка #39. Пока не подтверждено, что HCS не
  доставляет `SystemExited` для VM с подключённым адаптером, отцеплять адаптер
  значит заводить второе состояние работающей VM без причины.
* **Снятие запрета `NetworkMode::Nat`** в `create_vm`/`update_vm` — #44.
* **Очистка endpoint'ов** при удалении VM и при `initialize` — #42.
* **`VmSummary.ip_address`** — #37.
